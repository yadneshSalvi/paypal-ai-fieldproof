# Restricted funding lifecycle

The cancellation and allocation domain now has a pure accounting projection, durable encrypted journal schema and an authorized organizer/Auditor reader. It is **not yet connected to a donor-choice UI, transfer executor, all existing funding consumers or hosted release**. The existing hosted cancellation review remains read-only. Nothing in these functions authorizes a payment, transfer or change of purpose.

`planProRataCancellation` freezes the current receipt versions and allocates the uncommitted balance by retained contributions after completed returns. BigInt products and deterministic largest-remainder allocation conserve every cent. A share exceeding its own original payment's return capacity is an explicit reconciliation conflict. Paid expenses and fees are never silently redistributed between donors.

`projectFundingPositions` preserves each original `SettlementReceipt`, economic alias and donor obligation. A paired assignment records the source purpose and destination purpose in one journal entry. Its destination is an allocation of the same receipt, not another settlement credit. The complete source journal must be contiguous, unique, scoped and balanced. Reversals retain their original entry and cannot exceed it. Recorded consent is checked against its original commit time; passage of time does not erase valid history.

Both Orders and invoice receipts share the same projection. Existing refunds, pending returns and spending exclusions remain distinct. After any assignment, a receipt with deductions requires explicit complete attribution matching the current receipt version and every aggregate counter. A provider refund discovered later cannot silently become extra destination funding. Expense reservations and paid amounts remain attached to their actual package and are subtracted only from its available balance. Negative positions fail closed for reconciliation. Excess liabilities remain at the original purpose and cannot be transferred as support.

Schema 14 adds append-only funding assignments and versioned deduction attributions. Encrypted documents bind their exact row identity, digest, source receipt and workspace. A database guard rejects a foreign source before insertion. The canonical reader loads the complete conditional-credit journal, preserves separate checkout exclusion, and checks current organizer/Auditor authority before disclosing the result. Malformed legacy expense ownership fails closed instead of silently disappearing from available-fund calculations.

Every change to a receipt's saved content now advances its version once; a repeated identical write leaves its version unchanged. The new reader requires current deduction attribution after reassignment, so an external return cannot leave stale credit available to the destination. Earlier receipts and journal entries are retained. Schema readiness checks repair missing or disabled history/version guards.

The next integration must authenticate exact donor consent and current memberships, lock source and destination policy versions, commit balanced journal and current deduction versions transactionally, and update every funding consumer together. Payout selection, collections, public proof, Studio, community updates and planning must agree before transfer execution is enabled. Existing expense allocation history must not be rewritten to make a proposed refund possible.

Validation covers the 30 domain checks plus eight real PostgreSQL funding-storage cases and database repair coverage. All 376 application regression tests and strict non-incremental type checking pass. The first broad test run exposed shared test-fixture quota pollution; the new funding suite now owns and removes a separate schema. Application spending limits were unchanged. Provider calls: zero. No hosted migration or deployment is claimed by this checkpoint.
